# 我如何处理 issue（TRIAGE）

一个人维护，时间有限。这份文档的作用是：**让你知道什么时候会有回应、什么情况下我不会修**，
以及把「等运维」变成「等一个具体的动作」。新 issue 会由 `.github/workflows/triage.yml`
自动打标签并回一条收集材料的评论，但那只是托管，判断仍然是人做的。

## 响应节奏

- **通常一周内看一次**：工作日晚上 + 周末批量处理，不是当天回。
- 排队顺序按风险，不按时间：
  1. **数据安全**（误删、还原失败、隔离区损坏）—— 优先，会中断其它事；
  2. **崩溃 / 启动失败 / 看板打不开**；
  3. **计划与实际严重不符 / 分类明显错误**；
  4. 体验、文案、性能优化；
  5. 新功能。
- 急事（数据可能丢）在 issue 里加 `data-loss` 标签说明，我看到会先看。

## 标签含义

| 标签 | 含义 | 你要做什么 |
|---|---|---|
| `needs-triage` | 还没定性 | 等我看 |
| `needs-info` | 材料不够，无法复现 | 补 `diskmon-go.exe diag` 的输出 |
| `bug` | 已确认的问题 | 等修复版本 |
| `enhancement` | 已接受的功能请求 | 可能很久，也可能不做 |
| `data-loss` | 涉及数据安全 | 优先处理 |
| `stale` | 21 天没动静 | 补料即可复活 |

## 我会怎么判断一个 bug

1. **是不是最新版本**：旧版本已经修过的直接关掉并指向 CHANGELOG。
2. **是不是设计如此**：先对 [FAQ.md](FAQ.md)（隔离区共用盘符所以空间不立刻回来、
   进程归因是近似值、只能扫一个盘……）。是的话，把 FAQ 补一条而不是改代码。
3. **能不能复现**：没有 `diag` 输出、没有步骤的，挂 `needs-info`，**不猜**。
4. **修还是不改**：只在不破坏三条安全不变量的前提下修（只读监测、隔离优先、L2 需三道确认）。

## 什么会被直接关掉

- **重复**：指向已有 issue。
- **缺材料且长期无回应**：`needs-info` 21 天后提醒，再过 14 天自动关（`.github/workflows/stale.yml`）。
  关掉不是拒绝——补上材料重开即可，不用道歉。
- **要求实现会破坏安全模型的改动**（比如「加个跳过隔离区直接删」）：明确拒绝并说明原因。
- **和本项目定位无关的**：例如把它当成系统清理全家桶（改注册表、清 WinSxS 等），指向系统自带工具。

## 每周 15 分钟例行（这就是「托管」的全部真相）

自动化只能做到「收集材料 + 设定期望 + 清理无回应的队列」。真正的处理是这四步，加起来通常一刻钟：

1. 打开 issue 列表，按标签筛 `needs-triage`；能定性就改成 `bug` / `enhancement`，不能就补一句还缺什么。
2. 看 `needs-info` 里新补材料的：有 `diag` 的，按「版本 → 复现 → 分类」三步判断。
3. 修完一个就发版本（见下），并在 issue 里写清「哪个版本修的、怎么验证」。
4. 扫一眼 `stale`，确认没有真问题被误挂。

## 发版本时顺手做的事

- 改 `CHANGELOG.md`（用户看的是这个，不是 commit log）；
- 版本号进 `main.go` 的 `version`，`build-release.sh` 打 zip；
- Release 说明里写「如果你遇到 X，升级到这个版本」——能让下一个来搜的人直接闭嘴。

## 收到「清理后空间没变」类反馈时

先确认隔离区在不在同一个盘：`diag` 里的「数据目录」。同一盘符 = 空间在隔离区清空后才回来，
这是设计如此（见 FAQ 第 2 条）。如果是跨盘配置（数据目录在 D:），那就是真的没清干净，当 bug 查。
