# 逐文件索引：建了，但**故意不接线**

记录时间：2026-10-29。对应的实现：`mft_index.go` / `mft_index_test.go`（全仓零调用点）。

这份文档存在的理由只有一个：**下一个看到「有个索引却没人用」的人，不该以为这是半成品。**
它是量过代价之后主动停下的结果。

---

## 一、它是什么

以 FRN 为键，存每个文件的大小与链接数：

```
DNMF 魔数 | 版本 | 卷标 | builtAt | 条数
 每条：{ ΔFRN(uvarint), size(uvarint), links(uvarint) }
FNV-1a 校验
```

加校验不是因为洁癖：**半份索引看起来能用**，比没有索引更危险——它会被当成完整结果喂给增量应用。

## 二、五个数字（C:\ 全卷，**目录遍历口径**）

这台机器不是管理员，MFT 直读量不了，所以集合是「遍历可见集」：565 处目录读不进、
1,164 个文件打不开、junction/硬链接造成约 6.3 万条重复路径。**FRN 差值与总体积因此略偏高。**

| 项 | 数字 |
| --- | --- |
| 条数 | 635,740 |
| 落盘体积 | 2,811,686 字节 = **2.68 MiB**（4.42 字节/条） |
| 构建耗时 | **250.3ms**（排序 + 填表，不含采集） |
| 加载耗时 | **19.2ms**（含 ReadFile，系统缓存命中；无权限清缓存做冷读） |
| 常驻内存 | ≈10 MiB —— **按 17 字节/条算的理论值，不是实测** |

小样本对照（System32，24,781 条）：118,409 字节 / 4.78 字节/条 / 构建 5.9ms / 加载 1.0ms。
这个样本可由 `DISKMON_MFTIDX_MEASURE=1 DISKMON_MFTIDX_ROOT=... go test -run TestMeasureMftIndex` 复现。

反例：同一跑里实测常驻内存 111,848 字节，而理论值 421,277（17×24,781）。
**差值三倍多，说明 HeapAlloc 差值法在小集合上太噪。** 所以上表最后一行只当算术看。

## 三、体积不是问题，采集才是

`go.mod` 那个「别为省一次全扫换来一份一百多 MB 缓存」的担心**没有发生**：2.68 MiB。

真正的问题是采集：

| 采集方式 | 耗时 |
| --- | --- |
| 目录遍历 | 4 分 16.6 秒 |
| MFT 直读 | 2.56 秒 |

**所以这张表必须搭 MFT 扫描的便车建**（建表只占 2.56s 的 10%），绝不能拿遍历建。
拿遍历建 = 为省一次全扫先付掉四分钟。

## 四、为什么不接线

### 1. 产地与消费者在常驻路径上是错开的

`scan_mft.go` 里那个 `files` map 是局部变量，range 完就丢；
`useMftEngine` 只在一次性 `scan` 为真，**常驻路径（watch/tray/serve）恒为 false**。

注释里写明了为什么不能开：早先 MFT 曾写在 `ScanRootCached` 开头，结果常驻每 5 秒读 3 秒 MFT，
**把加速用成了减速**。这条不是疏漏，是踩过的坑。

### 2. 过期是静默的

表只描述建表那一刻。同一次会话里同一个文件再写一次，增量就会拿**旧大小**做「减旧加新」，
体积越算越偏，而且没有任何报错。

不解决这条就接线，等于用「快但错」换「慢但对」——而这个项目最贵的一条规矩是
宁可慢，不许给偏小的数字。

## 五、如果将来要接，最小切片在哪

不是全盘接线，只需要一条路：

```
main.go: scan 子命令 → useMftEngine = true
scan.go:378 → ScanRootCached
scan_incremental.go:506  cachedMftScan(...)     消费侧
scan_incremental.go:528  scanVolumeViaMft(...)  生产侧
```

**产和消费在同一个函数里，中间只隔十几行。** 在这条路上：

1. `scanVolumeViaMft` 多返回一个东西（map 或建好的索引）；
2. `saveMftScanCache` 同时落索引；
3. `:528` 之前加一个分支：先试「加载索引 → 读增量 → 应用」，不成就走原来的 MFT 全读。

第 3 步才是提速点：现在**只要卷上有任何改动就整份重读 $MFT**；接上之后，增量能应用时才算增量。
过期问题在这里也天然缓解——应用完立刻重写快照与索引，不存在「表比数据新」的窗口。

## 六、但这次仍然不做，因为收益只有两秒

```
现在（有改动时）  读 110 万条 $MFT   约 2.56–3 秒
接上之后          应用增量           约 0.3 秒
```

省两秒，代价是签名改动 + 新分支 + 一张会过期的表 + 「接错就是快但错」的风险。

而且**它只对 `diskmon scan` 有效**：托盘常驻走的是遍历 + USN 脏集合，零受益；
非管理员走的也是遍历。这两条加起来是绝大多数人的实际情况。

**真正值得动的性能只有一处：非管理员的首次冷扫（4 分钟级）。** 那张单不在这里。

## 七、什么条件下应该重新考虑

- 命令行 `scan` 变成常见用法（例如被脚本/CI 反复调用）；
- 或者卷大到 MFT 读取明显超过 3 秒；
- 或者常驻路径改成也用 MFT（那时第一条理由消失，但必须同时解决过期）。

三条都不成立时，这张表就留在仓库里当零件，**不要接**。
